## Architectural directions for the operator

These are inspection areas, not tested interventions, settings to copy, or predicted gains. Preserve checkpoint, precision, tokenizer, sampling, prompt semantics and the harness's lossless acceptance criteria. Quantization is part of the reference checkpoint, not permission to introduce additional quantization or pruning.

1. **Nano 3 30B**: hybrid Mamba-2/attention/MoE; 128 routed experts, top-6 plus one shared expert, 52 layers. Areas: SSM state/cache lifecycle, expert dispatch and shared-expert execution, NVFP4 kernel coverage on sm_120, attention across longer contexts. Architecture verified from [NVIDIA config](https://huggingface.co/nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-NVFP4/blob/main/config.json). The official command is preserved in [existing recipe](../forge/recipes/nano3-30b-a3b-nvfp4.yaml). Its card-era FlashInfer environment requirements are a compatibility question, not a proven local execution path.

2. **Super 3 120B/A12B**: hybrid Mamba-2/attention, latent MoE with 512 routed experts, top-22 and one shared expert, 88 layers; config includes an MTP block. Areas: latent expert projections/dispatch, SSM state movement, NVFP4 execution, native prediction-head integration and verification, long-context state management. [Config](https://huggingface.co/nvidia/NVIDIA-Nemotron-3-Super-120B-A12B-NVFP4/blob/main/config.json); [official card](https://huggingface.co/nvidia/NVIDIA-Nemotron-3-Super-120B-A12B-NVFP4). The new recipe preserves the official command without adding speculative decoding. It relocates only the parser file path through `hardware.adapt` for the fleet working directory.

3. **Lightning 30B/A3B**: 52-layer hybrid, 128 routed experts/top-6 plus one shared expert. MTP attention/MoE blocks exist; DSpark is already enabled in the new reference. A separate DFlash companion is described by NVIDIA; its presence is not a mandate to change the reference. Areas: recurrent-state execution, sparse expert scheduling, NVFP4 kernels, proposal verification and launch overhead. [Config](https://huggingface.co/nvidia/NVIDIA-Nemotron-3.5-Lightning-30B-A3B-NVFP4/blob/main/config.json); [card and exact H100 DSpark command](https://huggingface.co/nvidia/NVIDIA-Nemotron-3.5-Lightning-30B-A3B-NVFP4). The prior Spark DSpark and H100 non-speculative recipes remain distinct references.

4. **GPT-OSS 20B**: approximately 21B total/3.6B active, 32 experts/top-4, 24 layers alternating full and 128-token sliding-window attention, native MXFP4 expert weights. Areas: expert routing and MXFP4 execution on sm_120, alternating attention paths, host/launch scheduling at short contexts. [Vendor card](https://huggingface.co/openai/gpt-oss-20b), [config](https://huggingface.co/openai/gpt-oss-20b/blob/main/config.json), [vLLM recipe catalog](https://recipes.vllm.ai/openai/gpt-oss-20b). The vendor's exact serve command is `vllm serve openai/gpt-oss-20b`; no drafter or new quantization is added.

5. **Bolt 74B/A9B**: Mamba-2/attention LatentMoE and C-RADIO vision tower. Compression yields heterogeneous routed-expert counts/widths; top-k is 9. Do not describe the global config's 512-expert field as a uniform per-layer count. Mixed IQ2-XXS experts, NVFP4 Mamba and Q8 embedding/output components; LiLiCorr is already enabled in the official command. Areas: heterogeneous expert dispatch, mixed-format kernel paths, recurrent state, proposal verification. [NVIDIA model card](https://huggingface.co/nvidia/NVIDIA-Nemotron-3.5-Bolt-74B-A9B-24GB). About 25.05GB target-plus-drafter artifact size is inherited from the catalog, not a measured VRAM allocation.

6. **Super 3.5 VL 120B/A12B**: hybrid Mamba-2/attention LatentMoE, 512 routed experts/top-22 plus shared expert, vision tower, native MTP blocks and separate LiLiCorr. Areas: latent-expert execution, SSM state, NVFP4 paths and speculation verification. [NVIDIA config](https://huggingface.co/nvidia/NVIDIA-Nemotron-3.5-Super-VL-120B-A12B-NVFP4/blob/main/config.json). Existing LiLiCorr recipe estimates approximately 76GB of target-plus-drafter artifacts; runtime headroom remains tight. The current text gate does not certify vision/video output equivalence. NVIDIA's [NIM deployment guide](https://docs.nvidia.com/nim/large-language-models/latest/get-started/advanced/get-started-nemotron-3.5-super-vl.html) lists server-class configurations, not evidence for this single Max-Q command.

**Reserve: Nano 3 4B FP8/BF16.** A 42-layer dense hybrid, approximately 5.27GB FP8 artifact size in the existing catalog; CPU scheduling/launch overhead and SSM/attention boundaries are plausible inspection areas, not diagnosed bottlenecks. Fits both cards as a capacity estimate and is not cached. [Official recipe](https://recipes.vllm.ai/nvidia/NVIDIA-Nemotron-3-Nano-4B-BF16) and [NVIDIA article](https://huggingface.co/blog/nvidia/nemotron-3-nano-4b) were reviewed. No absolute sm_120 serving number was verified, so this ranks below targets with public hardware-specific reports.

## Reference commands, setup and adaptations

Each YAML's `serve.quoted` holds the official command, `serve.source` cites its provenance, and `serve.args` is the executable argument list after model-variable substitution. No recommendation or result is placed in a drafter note or workload. New files:

- [Bolt 5090](../forge/recipes/bolt-74b-lilicorr-5090.yaml): official Bolt command and LiLiCorr checkpoint unchanged; **only** `--max-model-len 4096 --gpu-memory-utilization 0.95` are applied for `rtx5090_32g`. This is the user-specified fixed-cache fit adaptation, not a measured optimization. Both reference and candidate receive it. c1 only. The original Bolt file remains unchanged outside published metadata. NVIDIA prerequisites are the pinned nightly, `b12x`, downloaded kernels, and its reasoning parser; none were installed here.
- [Super 3](../forge/recipes/super3-120b-a12b-nvfp4.yaml): NVIDIA vLLM 0.20.0 reference command, fleet's existing later pinned runtime image; parser `/app/...` becomes the same file in the recipe working directory on the PRO class. No performance flags are added.
- [Lightning H100 DSpark](../forge/recipes/lightning-30b-a3b-nvfp4-dspark-h100.yaml): official H100 low-latency command, DSpark companion and three proposal tokens. The artifact estimate is 22.91GB including drafter; the new file makes no 32GB fit claim for the default long context and state allocation.
- [GPT-OSS](../forge/recipes/gpt-oss-20b-mxfp4.yaml): vendor's bare serve command, later pinned fleet runtime; vendor memory target is 16GB, exact download bytes were not established.

Always obtain the expanded reference through `forge.recipes.get(id, gpu_class)` before `normalize_recipe`. Normalization of raw YAML alone does **not** apply `hardware.adapt`. This matters especially for Bolt 5090 and the Super 3 parser path. Catalog source commands are historical references, not claims that the pinned fleet runtime is the exact engine behind a published number.

The vLLM recipe catalog was cross-checked for [Lightning](https://recipes.vllm.ai/nvidia/NVIDIA-Nemotron-3.5-Lightning-30B-A3B-BF16), [Nano 4B](https://recipes.vllm.ai/nvidia/NVIDIA-Nemotron-3-Nano-4B-BF16), and GPT-OSS. Model cards supplied exact commands where the rendered catalog exposes only overview/client sections.

## Record readiness and no-leak boundary

The six targets are research leads with catalog-loadable recipes, **not six already-qualified records**. Before an operator can claim an external record, a later authorized run needs the same hardware SKU/power class, checkpoint and precision, engine/reference definition, concurrency, input/output lengths, tokenizer/request construction, sampling, cache/warmup policy, and metric denominator. Preserve the original report's censoring and EOS behavior. Match the public workload separately from the hidden lossless gate; do not replace hidden gate prompts with public benchmark prompts.

The existing schema carries output caps and concurrency but does not synthesize exact ISL. Therefore the `:c5`, `:c16`, and `:c32` variants align selected output/concurrency values only; their public harness prompts do not recreate the external workloads. Published metadata is descriptive and is not used as a measured gate reference. PRO results require edition/power-limit clarification before a Max-Q comparison.

Static inspection found `mission_brief` and the profile tool select operational fields rather than serialize `published`; normalizing a recipe retains the metadata in memory. The report is outside `forge/agents`, is not referenced by prompts, and is not installed as a recipe extra file. The added unittest checks that a metadata sentinel never appears in mission briefs. This is a check of current paths, not a promise that arbitrary future code cannot expose metadata. Do not copy recipe research metadata or this report into an agent-readable workspace.
